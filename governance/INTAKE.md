# Пополнение из чатов и результатов Codex

Рабочее предложение STRUK-LOCAL-012. Реализована структура и журнал, но фоновой синхронизации нет. Чат не имеет гарантированного доступа ко всей будущей истории и вложениям.

## Явный запуск

В конце содержательной сессии использовать фразу: «Зафиксируй результат в YS Metodology: новые источники, решения, противоречия, открытые вопросы, изменения плана». Чат с доступом к корню выполняет цикл ниже. Для недоступного чата нужен доступный экспорт или файл; нельзя восполнять его по заголовку.

## Один цикл пополнения

1. Прочитать PROJECT, PLAN, DECISIONS, реестр источников и актуальную общую память. Проверить правильный корень и действующие права.
2. Зарегистрировать исходник: устойчивый source_id, путь/chat/message, автор/роль, дата события и получения, версия/hash, доступ и конфиденциальность. Файлы оставить на месте; ограниченные выдержки хранить в governance/sources, клиентские оригиналы — только по отдельному согласованному пути.
3. Найти дубли по source_id/message_id и SHA-256, затем по тезису. Повтор не создаёт новое решение. Новая редакция того же документа получает связь supersedes, старый hash не исчезает из журнала.
4. Разобрать материал на факт, наблюдение, гипотезу, предложение, прямое решение, результат испытания. Указать говорящего. Реплика ассистента «готово» требует файла/проверки; молчание пользователя не принятие.
5. Сопоставить с DECISIONS и CONTRADICTIONS. При расхождении сохранить обе версии, контекст и scope. Не считать более поздний текст автоматически истинным; явное последующее решение может заменить прежнее в своей области.
6. Внести минимальные изменения в тематический файл; не копировать весь чат. Обновить PLAN/OPEN-QUESTIONS и CHANGELOG. В PROVENANCE.jsonl добавить событие с перечнем затронутых записей и основанием статусов.
7. Проверить ссылки, заполненность происхождения, допустимые статусы, отсутствие клиентских данных в публикационных местах. Прочитать записанные файлы обратно. Сравнить оригиналы по hash, если их сохранность входила в работу.
8. Сообщить: какие записи изменены, где, чем подтверждены, какие вопросы требуют Юрия. Краткий итог в Memora — только после поиска дубля, с project/author/status/recorded_at; без диалога, вложений и клиентских деталей.

## Регулярность и приёмка

Предложено: пополнение после каждого значимого результата; раз в неделю по явному запросу Юрия — сверка противоречий, открытых источников, критериев и плана. Для автоматизации сначала определить расписание, источники доступа и допустимый объём записи. Сейчас автоматизация не создана.

Критерий завершённого пополнения: у каждого нового существенного тезиса есть источник и роль, статус, scope и дата; подтверждение записи прочитано с диска; противоречия не скрыты. Нет источника — записать ограничение вместо содержания.

Машинный формат журнала: `event_id, recorded_at, author, source_ids, record_ids, action, status, affected_files, limitations`. Для клиентского материала сохранять ссылку и разрешённый обезличенный вывод, не текст по умолчанию.
