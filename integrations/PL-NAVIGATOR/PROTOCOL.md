## Один источник в каждой области

Нормативный смысл — документы методологии с источником и статусом. Исполняемый каталог/формулы/схемы/генераторы — Code у PL, с привязкой к версии и источнику методики. Изменение файла реализации не принимает новое правило. Если правило не формализовано, открыть точный вопрос здесь вместо выдуманной формулы.

Ссылка из методики на исполняемый артефакт должна включать версию/ревизию, когда это влияет на интерпретацию. Старые оценки читаются со своей версией. Если отображаемое имя каталога не менялось при изменении вопросов/условий, оно не доказывает тождество снимков: нужна проверяемая привязка к конкретному содержимому (например, зафиксированная версия и контрольная сумма). При несовместимости сохранить старый материал и явно показать предел, а не тихо переинтерпретировать ответы. Миграция — отдельное явное действие, а не скрытое изменение старого вывода при открытии.

Рабочий кейс — единая запись; таблица, паутины и правая панель являются представлениями одних вопросов/ответов/оснований, а не тремя независимыми оценками. Общий источник можно связать явно; это не копирование ответа родителя во все дочерние узлы.

## Состояния и достаточность

Пользовательские состояния: «Готово», «Частично готово», «Не готово», «Нет ответа». Неизвестный факт не равно известному невыполнению. «Не используем» — отдельное обоснованное исключение из расчёта, не доказательство готовности.

Будущий вопрос остаётся будущим в выбранном контексте и версии методики; его нельзя массово исключать для улучшения оценки. Снятие исключения восстанавливает исходное состояние/ответ, требует пересчёта и при необходимости сверки связанных решений.

Продукт и бизнес имеют независимые стадии, рассчитываемые из условий. Выбор цели не меняет достигнутую стадию. Заполнение формы, выбранная задача и её исполнение сами по себе стадию не повышают. Локальный прототип не доказывает SaaS, самокейс не доказывает спрос, интерес не доказывает платёж.

## Минимальный контракт данных и передачи

PL определяет конкретную схему и API. Методические требования к контракту:
- устойчивые ID проекта и вопроса, независимые от приложения и видимого заголовка;
- тип проекта, владелец/права, ревизии данных, схемы и методики;
- источник/дата/происхождение ответа, факт/гипотеза/наблюдение/вывод с разными статусами;
- исключение и причина без утраты исходного ответа;
- выбранное решение с целью, основаниями, проверкой, зависимостями;
- исполнение, результат, принимающий и повторная оценка раздельно;
- производный тест: исходный проект/ревизия, преобразования и отдельная область записи.

Неподдерживаемую/повреждённую схему не перезаписывать. Смена версии или повторный импорт не создают незаметный дубль и не разрешают потерять дополнительные поля. Разные ID сами по себе не доказывают разграничение доступа.

## SMART и приватность

Цель переноса — Cases/clients/SMART внутри PL Navigator. До проверенного переключения рабочий источник D:/Clients/Smart. После — один текущий источник, прежний остаётся неизменным. Удаление исходной папки не поручено.

Клиентские выводы и заполнение SMART на паузе. Перенос не разрешает переоценку. Тесты только в Cases/tests/SMART или synthetic; автоматической записи результатов теста назад в клиента нет.

Клиентские документы, частные тестовые производные, полный JSON/аудио/диалоги/секреты не входят в методический Git, публичный seed/build, общие логи, Memora и общий codebase/Qdrant-индекс. Cases исключается проверенным проектным правилом до первого копирования; при обнаружении старых записей требуется адресная очистка существующим индексатором и подтверждение результата, без второго индексатора/глобальной перестройки. В Code допустимы только проверенные синтетические фикстуры без клиентских сведений. Материалы исторических дашбордов остаются внутри соответствующих закрытых версий.

## Обмен и полномочия

YS → PL: цель, относящееся требование/источник, версия, разрешённая область, выход и проверка. PL → результат в своём чате/Admin: точные пути, выполненное, доказательства, непроверенное, разрывы и дальнейшее действие. YS читает артефакты, а не принимает слово «готово».

Методическое замечание: пример → наблюдаемая ошибка → последствия → предлагаемое правило → тест → статус решения. Клиентские исходники для этого не копируются сюда.

Юрий прямо разрешил координацию с PL и реализацию плана. Пересылка рабочего задания PL выполнена отправителем YS; получателю не выдаётся автоматическое право писать обратно другим чатам. При необходимости YS читает его результат. Это не требование ручного копирования пользователем.

Текущий пакет документации пишет YS; Admin/Code/Cases — PL. Общие AGENTS/PROJECT/PLAN и индекс Git здесь не менять параллельно с владельцем STRUK. Существующие прямые разрешения сохраняются; конкретный новый риск/внешнее действие выделяется отдельно.
