# Методические условия проверки PL Navigator

Дата: 26.10.2026, Europe/Moscow. Основание — [утверждённый план](PLAN.md).
Статус документа: критерии для исполнения; перечисление сценариев не означает их прохождение.
Исполняемые тесты/результаты создаёт PL в своём проекте. Здесь — только правила, ожидаемые результаты и методическая сверка.

## Что считается доказательством

Для проверки сохранять: кейс/ревизию, версию схемы и методики, действие, ожидаемый и фактический результат, путь свидетельства, автора проверки, пределы. Тестирование кода, наблюдение интерфейса, профессиональная приёмка Юрия, применение и эффект — разные результаты.

Собственный отчёт исполнителя недостаточен для независимой приёмки. Не требовать только количественных KPI: качественное наблюдение допустимо, если отвечает проверяемому требованию.

## Поэтапная приёмка

| Этап | Необходимый результат | Нельзя считать доказательством |
|---|---|---|
| Организация | подтверждённые роли, запись, зависимости, привязки и независимая проверка | созданные папки или прочитанный скилл |
| Перенос кода | ведомость/сверка, воспроизводимый запуск и нужные регрессии | совпадение числа файлов или один SHA HTML |
| Перенос SMART | совпадение файлов/версий, рабочие ссылки, явные пределы browser-state, независимая сверка | копирование папки как доказательство переноса localStorage |
| Изоляция проектов | устойчивые ID и проверенное разграничение чтения/записи/сброса | разный заголовок или разные JSON-файлы без прав |
| Самокейс | реальные основания по 18 направлениям, очередь/причины глубины | ответы ИИ без источников или зелёная паутина |
| У–К | выполненное улучшение, независимая проверка, применение/наблюдаемый результат | сохранённая задача или галочка «сделано» |
| Ограниченный SaaS | пользователи/права, серверные ревизии, восстановление, выпуск | локальный просмотр в одном браузере |
| Внешний пилот | два внешних PL, по проекту и повторному обновлению, наблюдения полезности | собственный кейс, интерес или обещание заплатить |

При существенном непрохождении исправить разрешённую часть и повторить затронутые сценарии. Не объявлять весь этап принятым с необъяснённым блокирующим расхождением. Несвязанные безопасные работы продолжаются; внешний пилот/ответ SMART не останавливают внутренний цикл.

Этап 1 проверяет локальную независимость проектов и их хранилищ, достаточную для собственного кейса. Серверное межпользовательское разграничение обязательно на этапе 4 (C20); оно не требует строить весь SaaS до самокейса. Перед переносом клиента отдельно проверяются фактические права закрытой файловой области.

## Матрица обязательных сценариев

| ID | Сценарий | Ожидаемое поведение |
|---|---|---|
| C01 | Пустой проект/повторное открытие | Только структура; нет скрытых примеров, ответов, задач или выбранных целей |
| C02 | Ответ/статус/основание, save и reload | Точный ответ и происхождение восстановлены; ни один соседний вопрос не отмечен |
| C03 | Две вкладки меняют разные данные | Нет молчаливой потери, конфликт определяется/разрешается с сохранностью |
| C04 | «Не используем» без причины / с причиной | Без причины не принимается; с причиной исключается только назначенный элемент, исходный ответ сохраняется |
| C05 | Снятие исключения | Восстановление исходного ответа, согласованный пересчёт таблицы/паутин/связанных решений |
| C06 | Одно основание связано с несколькими вопросами | Явная связь не превращается в одинаковый ответ и статус всех вопросов |
| C07 | Смена проекта / сброс производного теста | Другой проект и реальный SMART не изменены |
| C08 | Повторный импорт / будущая или повреждённая схема | Нет незаметного дубля/перезаписи; ошибка названа; рабочие данные целы |
| C09 | Все затронутые уровни таблицы/паутин | Одинаковые вопросы, условия, состояния и источники на соответствующих узлах; счётчики имеют одинаковую единицу |
| C10 | Подсказка, раскрытие, возврат, смена круга | Текущий узел и контекст сохранены; данные не меняются от навигации; подсказки доступны на краях экрана |
| C11 | Ранняя стадия / будущие требования | Нет обязанности нагрузки/промышленной поддержки на уровне идеи без относящегося риска; будущий вопрос не ложный текущий провал |
| C12 | Независимые стадии и выбранная цель | Нельзя назначить достигнутую стадию вручную, продуктовый MVP не требует автоматически первых продаж бизнеса |
| C13 | Нет ответа / известное невыполнение | Различаются; отсутствие данных не выдаётся за отсутствие свойства |
| C14 | Решение с изменившимся/исчезнувшим основанием | Решение остаётся в истории и требует явной сверки; зависимости удерживаются; фильтр их не отменяет |
| C15 | Задача выполнена / результат не принят | Ответы и стадия не становятся готовыми автоматически; видно различие исполнения и приёмки |
| C16 | Новое проверенное основание результата | Повторная оценка явная, с версией и источником; история до изменения доступна |
| C17 | Изменена методика | Старая оценка сохраняет свой снимок; различное содержимое под одинаковым именем каталога опознаётся и не переинтерпретирует ответы молча; изменение оценки из-за шкалы не считается эффектом продукта |
| C18 | Поздние стадии: сохранение/обновление/завершение | Оценка учитывает выбранный и обоснованный результатами/ресурсами путь, последствия и обязательства; проверено соответствующее действие, выбор списка сам по себе не достаточен; рост не обязательный универсальный исход |
| C19 | Прерывание сохранения / восстановление | Рабочая ревизия не уничтожена; восстановление проверено фактически |
| C20 | SaaS: чужой пользователь/проект | Сервер отклоняет неразрешённое чтение/запись, включая прямое обращение вне интерфейса |
| C21 | Публичная сборка, Git, логи и общий индекс поиска | Нет клиентских материалов, приватных производных/секретов. Перед новыми копированиями проверяется исключение Cases. Уже произошедшее попадание сохраняется как нарушение в истории; исправление принимается отдельно по запрету новых включений и подтверждённому удалению прежних записей, а не по одному запрету запросов |
| C22 | Самокейс оценивает улучшение собственной шкалы | Изменение продукта и изменение критериев разделены; есть независимая проверка и контрпример |
| C23 | План роста / фактическое расширение | Выбор расширения не присваивает стадию; достигнутое расширение проверено по результату, качеству, нагрузке и затратам |
| C24 | Собственный проект и цикл в интерфейсе | Кейс реально открывается в том же сервисе; относящиеся ответы, основания, действие и контроль доступны/сохраняются/перечитываются. Отдельный JSON-отчёт без такого сценария не принимается как реализация У–К |
| C25 | Передача первого входа и первого результата | Проверен именно выданный получателю путь, с его исходным состоянием/необходимыми условиями. Переход из выданного файла/страницы приводит к рабочей форме; защищённые действия остаются защищёнными; после входа возможен первый содержательный результат. Тестовый прогон и реальный вход владельца учитываются отдельно |

Не повторять весь набор после каждой правки без причины. Сначала затронутые сценарии и обязательные регрессии на границе этапа; расширять при новых рисках/изменениях. Не создавать тесты, зеркалящие только реализацию.

## Как вести глубину собственного кейса

Обзор покрытия — методическая запись внутри собственного проекта PL, не дополнительная анкета клиента. Для ветви: устойчивый узел/версия, рассматриваемый круг, основание, выявленное неизвестное/несоответствие, причина углубления или возврата, следующее действие.

Статусы обзора не подменяют статусы ответа: рассмотрено/требует углубления/отложено до контекста описывают работу, а не готовность свойства. Будущая ветвь не получает «Не используем» без предметного основания. Данные не копируются между стадиями ради полноты.

Первый обзор всех 18 направлений может указать недостаток сведений; он не обязан достигнуть идеи по каждой шкале. Каждый следующий цикл закрывает значимое неизвестное или реализует действие; количество заполненных пунктов само по себе не эффект.

## Контроль пользы

Внутренний цикл: удалось ли из конкретного основания выбрать действие, выполнить, проверить результат и обоснованно принять следующее решение?
Внешний пилот: время до полезного плана, места необходимой помощи, ошибки, повторное использование, фактическая польза действий и затраты поддержки. Порог коммерческого успеха не выдумывать до фактических наблюдений/решения Юрия.

Разбор фактического сбоя первого входа Юрия и минимальное правило передачи: [Первый результат и приёмка](../../methodology/FIRST-RESULT-ACCEPTANCE.md). Успешные технические проверки не объявлены доказательством этого пользовательского пути.
